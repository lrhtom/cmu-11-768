进阶 RL 算法：功劳分配、稳定的更新、可靠的奖励、向老师学

2. 组基线让失败也有信号，但分不清是哪一步的功劳

组基线就是拿同一题几次尝试的平均分当及格线。高于它的加分，低于它的扣分。

普通 REINFORCE 成功就把整条轨迹的概率往上推，失败什么都不做（讲义第 6 页）。这样方差大，难优化 3:29。我们希望失败也提供学习信号，奖励也比 0 和 1 更细 4:16。

上一讲的 GRPO 就是第一步（讲义第 8 页）。同一个任务采四次，用组平均 (1+0+0+0)/4 = 0.25 当基线。成功的权重是 +0.75，三次失败各 −0.25 5:00。

rewards = np.array([1, 0, 0, 0])     # 同一个任务采四次（讲义第 8 页）
weights = rewards - rewards.mean()   # 组平均 0.25 当基线
print(weights)
# 输出: [ 0.75 -0.25 -0.25 -0.25]
# 踩坑：成功轨迹的每一步都拿 +0.75，中间那步错误也跟着被奖励
# 作业 3 考点：作业 3 的优势就是这样算的。只减组均值，不除以标准差，不加 KL

这像全班按平均分排名。考得好的加分，考得差的扣分，没人白考。

但这还不够细（讲义第 9 页）5:005:42。成功的轨迹中间可能错过一步，后来又救回来了。给整条轨迹正权重，就把这个错误也奖励了。失败的轨迹可能前面一直做得很好，到最后才出岔子。没必要把前面有用的工作全罚掉。这就是功劳分配问题，要的是回合级的奖励 6:22。

3. 价值函数预测：从这一步出发还能拿多少奖励

价值函数就是一个打分员。它看一眼现在的历史，猜最后能拿多少奖励。

上一讲的剩余回报 Rt，是 ht 之后还剩的奖励之和（讲义第 10 页）6:227:03。只有最终奖励时，成功轨迹 A 上处处是 1。失败轨迹 B 上处处是 0。这样还是分不出哪一步好。

只看到最终奖励，怎么知道哪一步有帮助？同学们提了几个想法 7:45。比如写 rubric 拿细粒度奖励，找成功轨迹共有的动作。还有给"轨迹更短"这类额外奖励。讲师说都不错，有的后面会讲 8:29。最典型的做法是训练一个模型。它预测"照现在这样，智能体会不会成功"。这就是价值函数 10:00。

直观上是这样（讲义第 12 页）。从 B 的历史 h3 出发，用同一个 rollout 策略 μ 再跑 10 次。3 次成功、7 次失败（示意），期望剩余回报约 0.3 10:43。跑无穷多次，就是这个策略下的价值 11:24：

Vμ(h3) = 𝔼μ[R3 | h3]

每一步都这样采太贵。所以训练一个评论家（critic）Vφ(h) 去预测剩余回报。训练用平方误差（讲义第 13 页）11:2412:06：

LV(φ) = 𝔼t[ ( Vφ(ht) − Rt )² ]
outcomes = np.array([0, 1, 0, 0, 1, 0, 0, 0, 1, 0])  # 从 h3 再跑 10 次，3 次成功（示意）
for v in (0.6, outcomes.mean()):
    print(v, round(np.mean((v - outcomes) ** 2), 2))  # 预测 v 时的平均平方误差
# 输出: 0.6 0.3
# 输出: 0.3 0.21
# 平方误差在均值处最小，所以评论家学到的就是"从这里出发的成功率"

复用这 10 个结果。预测 0.6 时，平均平方误差是 [3(0.6−1)² + 7(0.6)²]/10 = 0.30。预测均值 0.3 时最小，是 0.21。这像天气预报员。他不知道明天下不下雨，但长期说 30% 最准。

评论家怎么搭（讲义第 14 页）12:0612:4913:32：

做法怎么训练代价
独立的价值网络（更常见）有自己的主体和输出层，价值损失训练整个网络。例子是 InstructGPT。要训练两个模型，训练一个已经够难了
策略主体上的价值头在策略模型的表示上，加一个很小的线性价值头 φ。用 stop-gradient 让价值损失只训练这个头。策略损失仍训练主体。例子是 MIXER。几乎不加参数

输出端也有两种。一是直接回归一个数。二是问模型"这条轨迹好不好？是 / 否"。再用 P(是) / (P(是) + P(否)) 当预测 13:32。第二种只适用于奖励在 0 到 1 之间。但它能复用模型本身的先验，效果不错 14:2115:03。评论家可以和策略同时用 RL 训练。

课堂问答：模型能判断动作对不对，何不直接生成对的动作 15:50？讲师给了两个理由。一是价值函数只看历史，不看动作。它判断的是"现在的局面好不好"。二是判断自己做得糟，往往比知道下一步怎么做容易得多。区分好坏轨迹，比生成好的下一步容易 15:5016:31。

4. TD 误差看一步的好坏，GAE 把后面几步也算进来

一步的功劳，就看这一步前后价值涨了还是跌了（讲义第 15 页）16:3117:15：

δt = rt+1 + Vφ(ht+1) − Vφ(ht)

这叫时间差分（TD）误差，这里不打折扣。假如一个动作很糟，比如不小心删了代码库，价值一下掉到 0。这从 δ 上就能看出来 17:1517:56。

拿轨迹 B 的最后三步算一遍。V(h3) = 0.3，V(h4) = 0.6，V(h5) = 0.4。B 在 a5 之后结束，V(h6) = 0，奖励都是 0。于是 δ3 = +0.3，δ4 = −0.2，δ5 = −0.4。

TD 误差还要变成每一步的优势。最常用的是 PPO 用的广义优势估计（GAE，讲义第 16 页）17:5618:3819:19：

Ât = Σk≥0 λk δt+k = δt + λ Ât+1

λ = 0.5 时，Â3 = 0.3 + 0.5 × (−0.2) + 0.25 × (−0.4) = 0.1。a3 本身是好的一步，但后面跟着两步坏的。所以它的功劳被打了折扣。只要能训练出价值模型，就能估计每一步有多好。

V = {3: 0.3, 4: 0.6, 5: 0.4, 6: 0.0}   # 轨迹 B 的价值（讲义第 15 页），中间奖励都是 0
delta = {t: round(V[t + 1] - V[t], 2) for t in (3, 4, 5)}
A, lam = 0.0, 0.5
for t in (5, 4, 3): A = delta[t] + lam * A   # GAE 从最后一步往前递推
print(delta, round(A, 2))
# 输出: {3: 0.3, 4: -0.2, 5: -0.4} 0.1
# 踩坑：递推要倒着算。正着算时，A_{t+1} 还没算出来
# 作业 3 考点：作业 3 没有评论家，优势只用组均值当基线，所以用不到 GAE 和价值函数

这像球队复盘一次进攻。某一脚传球好不好，要看后面几脚接没接上。λ 越大，越看重后面。

λ 取多少？课上被问到时，讲师说训练 PPO 时常用 λ = 1 20:56。也就是不打折扣地把 δ 加起来。中间的 V 两两相消，只剩"实际的剩余回报 − V(ht)"。这相当于只看最终奖励 21:42。本机按讲义的数算过：λ = 1 时 Â3 = 0.3 − 0.2 − 0.4 = −0.3。这正好等于 0 − V(h3)。价值函数够好，或者有中间奖励（比如 rubric），才值得把 λ 设小。另外，讲义里的 μ 是 rollout 策略。完全同策略时，它就是正在更新的策略。后面讲异步时两者会不同 20:13。

另一个替代是过程奖励模型（PRM，讲义第 17 页）22:2623:09。价值函数是在学习过程中顺带学出来的。PRM 不一样，它事先单独训练，学"每一步对不对"。训练数据靠人工标注。讲义的例子是一道分数题的解答。标注员把"所以 x = 7"那一步标为错误。由 5x = 6x − 14 应该得 x = 14。讲师说它用得不算广，因为价值可以在训练中顺带学到。要是能拿到大量这类标注，可以先用它引导出初始价值函数。这样起点更好，训练会更快。

5. 异步 RL 不等掉队的，代价是用上旧策略的数据

异步 RL 让生成一直跑，攒够一批就更新，不再等最慢的那条。

智能体 RL 可能非常慢，作业里一定会体会到 23:51。先看同步 RL（讲义第 19 页）。几块 GPU 同时生成，或者几个智能体共享一个推理服务。一批里每条轨迹都结束了才更新。讲义的图还算客气 24:32。训练编程智能体时，常有一个"掉队者"。它要花别人两倍甚至四倍的时间。其他人全在干等 25:14。同步的好处是完全同策略。生成用的策略 μ 和正在更新的 πθ 一模一样 25:1425:58。

lengths = [3, 5, 9, 4]   # 一批四条 rollout 各要几个时间单位（示意）
idle = sum(max(lengths) - n for n in lengths)   # 同步：短的都要等最长的 9
print("sync idle =", idle)
# 输出: sync idle = 15
# 作业 3 考点：Part 3 的 AsyncGRPOTrainer，就是要把这段空等用起来

这像旅行团等最后一个游客上车。异步就是车先开，晚到的坐下一班。

异步 RL（讲义第 20 页）的做法不同。rollout worker 一直生成，攒够一批就开始更新。更新的同时继续生成，从不浪费时间等待。代价是一部分生成用的是更新前的旧策略 25:5826:41。讲师判断，现在认真做智能体 RL 的人都不用同步更新了。软件对异步的支持也已经很好。但异步会带来训练不稳定 27:22。系统层面的细节见本章第 2 讲的演示。

6. 过期的 rollout 要乘上新旧策略的概率之比

数据是旧策略采的，就给每个样本乘一个比值。这个比值说的是：新策略比旧策略更想采它多少倍。

一条 rollout 可能在 learner 更新之后才结束（讲义第 22 页）。三个可选的编辑，旧策略 μ 给 0.40 / 0.40 / 0.20。正在更新的 πθ 已经是 0.70 / 0.20 / 0.10。动作是 μ 采的，学习者却是 πθ 27:22。我们想要 πθ 下的期望奖励，实际拿到的却是 μ 下的 28:06。

修正办法是重要性采样（讲义第 23 页）28:4629:27。讲师问了一下，课上听说过的人出乎意料地少。

𝔼a∼πθ[R(a)] = 𝔼a∼μ[ ( πθ(a|h) / μ(a|h) ) · R(a) ]
mu = np.array([0.40, 0.40, 0.20])   # 旧策略给三个编辑的概率（讲义第 22 页）
pi = np.array([0.70, 0.20, 0.10])   # 正在更新的策略
R = np.array([1, 0, 0])             # 只有第一个编辑（加 None 检查）得 1（示意）
print(pi / mu, round((pi * R).sum(), 2), round((mu * (pi / mu) * R).sum(), 2))
# 输出: [1.75 0.5  0.5 ] 0.7 0.7
# 两边都是 0.7：在旧数据上乘了比率，就等于在新策略下求期望
# 作业 3 考点：比率按 token 算，ρ = exp(logπθ − logπold)，只看当前这个动作

正确的编辑比率是 0.70 / 0.40 = 1.75，不完整的编辑是 0.20 / 0.40 = 0.50。新策略下更可能的样本被放大，更不可能的被缩小 29:2730:10。这像拿旧问卷估计新人群。新人群里多的那类人，就把他们的票数加权。

麻烦出在长轨迹上（讲义第 24–26 页）30:1030:5631:4232:25：

7. 一次更新不能迈太大：裁剪、KL 和熵

过期数据的权重偶尔会大得离谱。裁剪就是给比率设上下限，出了界的部分不再算数。

讲义第 29 页是讲师实验室真跑出来的图，感谢助教 Aditya 34:31。图上画的是每个训练批里最大的重要性权重。最大"离策略程度"设为 1 时，曲线一直很平 35:18。这时只能用上一个策略的 rollout。放宽到 3 时，第 17 步左右冒出一个约 1,350 的权重。讲师口头说的是"一千四上下" 36:04。乘上这么大的权重，梯度一步迈得极大。整个训练可能就毁了。

w = np.array([0.99] * 99 + [2.0])   # 一批 100 个重要性权重，只有一个尖峰（示意）
stats = [w.mean(), w.min(), w.max(), w.std()]
print([round(float(s), 2) for s in stats])
# 输出: [1.0, 0.99, 2.0, 0.1]

# 作业特意提醒：均值接近 1 可能掩盖重尾。只看均值，就看不到这个尖峰

办法有点启发式，就是裁剪概率比（讲义第 30–32 页）36:0436:5337:37。PPO 的标准设置是下界 0.8、上界 1.2：

ct = clip(ρt, 0.8, 1.2)
JPPO(θ) = 𝔼t[ min(ρtÂt, ctÂt) ]
JCISPO(θ) = 𝔼t[ sg(ct) Ât log πθ(ut|u<t) ]

要最小化的损失是 −J。直观上是这样（讲义第 32 页）38:23。对有帮助的动作（Â > 0），比率超过 1 + ε 就不再给奖励。对没帮助的动作（Â < 0），比率低于 1 − ε 就不再惩罚。CISPO 用同一个裁剪比率，但把它当作不求梯度（sg）的固定权重 37:37。

def ppo(rho, A, eps=0.2):  # 讲义第 31 页：原始项和裁剪项取小的那个
    c = max(1 - eps, min(rho, 1 + eps))
    return min(rho * A, c * A)
for A in (1, -1):

# 输出: -1 [-0.8, -1.0, -1.4]

9. 组里全一样就没梯度：要么接着采，要么给部分分

GRPO 只能从组内的差别里学。所以要想办法让组里有差别。

DAPO 动态采样（讲义第 44 页）54:5355:36。奖励全同的组优势为零，就跳过它接着采。一直采到训练批里攒够奖励混合的组。讲师说用这个方法的人不算多，但大规模训练里用过。

部分和辅助奖励（讲义第 45 页）56:1857:00。任务越来越难，起点模型可能完全做不了。办法之一是先练简单任务。另一个是给部分奖励。最简单的就是"通过的测试数 ÷ 测试总数"。这样即使成功奖励是 0，也有非零分，算得出 GRPO 的优势。

checks = np.array([0, 1, 2, 1])    # 四条轨迹各过了几项检查（讲义第 45 页）
success = (checks == 4) * 1.0      # 只看成功：全是 0
partial = checks * 0.25            # 每项给 0.25 的部分分
print(success - success.mean(), partial - partial.mean())
# 输出: [0. 0. 0. 0.] [-0.25  0.    0.25  0.  ]
# 部分分 0、0.25、0.50、0.25，减去均值 0.25，组里终于有了差别

这像考试给步骤分。最后答案错了，前面写对的几步也能拿分。

  • "goblin 从哪来"：GPT 模型有一阵特别爱说 goblin、gremlin。比如"这个问题里有一堆编程小妖精"。原因是短暂引入的人设训练，给"书呆子气"的人设加分。当评审的语言模型认为，说 goblin、gremlin 很书呆子。这个偏好不断自我放大，比例越来越高。连没有人设提示时也会出现。

RL 系统：两种引擎、两边的交互、智能体 RL 的坑、框架设计

Apurva Gandhi 带大家逛一圈 RL 框架里会遇到的东西。采样和训练是两种完全不同的工作负载。所以框架拆成推理引擎和训练引擎，各自优化。推理端靠 KV 缓存、前缀缓存、连续批处理、投机解码。训练端靠激活检查点、前缀共享、各种并行。两边之间要传轨迹、同步权重、重放 MoE 路由。智能体 RL 还有几个公式里看不出来的坑。比如序列延伸、聊天模板删推理、必须 Token-In Token-Out。还有异步、飞行中的权重更新、复杂外壳。最后讲架构。从单程序多数据，走到"一切皆服务"。服务化以后，外壳无关的代理、在线 RL、多租户多 LoRA 都好做了。Tinker 就是这样的服务。

1. 采样和训练是两种活，所以拆成两个引擎

推理引擎只管采样，训练引擎只管前向和反向。两种活太不一样，所以拆开各自优化。

2. 推理端拿内存换速度，前缀缓存对智能体最值钱

推理端的优化，基本都是拿内存换掉重复计算。

KV 缓存（讲义第 9 页）10:23。逐个 token 解码时，不想为每个新 token 把前缀重新 prefill 一遍。于是把算过的 K、V 存起来，用内存换重算 11:05。但它非常大。Llama-3-8B 用 bf16，每个 token 128 KB。一条 32k 的轨迹约 4 GB，64 条约 256 GB。这还只是个小模型，RL 的 batch 现在又很大。要是训练和推理挤在一个引擎里，还得保留激活。留给 KV 缓存的内存就很少了。这也是拆开的好处之一 11:45。

# 输出: 128 KB 4.0 GiB 256.0 GiB
# 踩坑：64 条就远超单卡显存。所以前缀缓存和连续批处理对智能体 RL 很要紧

前缀缓存（讲义第 10 页）11:45。KV 缓存管一个请求之内。跨请求也有大量重复计算，智能体 RL 尤其多 12:27。GRPO 的组式 rollout 共享系统提示和同一个任务提示，然后才分叉。而且轨迹里每一步都是一个单独的 LLM 请求。只要前面的步骤是这一步的精确前缀，算过的就能复用 13:09。SGLang 用 RadixAttention，vLLM 有 Automatic Prefix Caching。

连续批处理（讲义第 11 页）13:5014:33。朴素的静态批处理里，请求长短不一，会有大量空闲。短的做完了，干等最长的那个。现代推理引擎每解码一个 token，就重新做一次调度决定 15:14。有请求完成、腾出了位置，就从队列里拉一个新的进来。

# 输出: 13 9

实际更复杂一点。prefill 是另一种负载，长提示的 prefill 会长时间堵住 decode 15:54。所以有分块 prefill，把长提示切块，和连续批处理交错执行。现在还有prefill / decode 分离（disaggregated inference）。专门一池 GPU 只做 prefill，另一池只做 decode 16:35。

课上有人问：已经有 radix attention 之类，分离 prefill 还有好处吗 19:27？讲师说用同样硬件时好处不太明显。主要好处是两种负载可以用不同的硬件。有的硬件很适合 decode，有的适合高吞吐的 prefill。助教补问 KV 怎么交过去。答案是要通信，通常经一个队列。prefill 池放进去，decode 池取出来 20:09。

3. 训练端多算一点，换回显存

训练端的优化，大多是多算一点，换回显存。

训练端要保留前向的激活给反向用（讲义第 13 页）20:56。所以很多优化都是"多算一点、省内存"。激活检查点的做法是这样。前向时每层只留输入，用完就扔 21:38。反向到这一层时，再把缺的激活重算出来。相当于多做一次前向，大约多花 33% 的时间，换来大量内存。不必对所有激活都这样做。框架一般有完整检查点和选择性检查点两种。显存吃紧时，它是你最好的朋友 22:21。

fwd, bwd = 1, 2              # 反向的计算量约是前向的两倍（常用估算，示意）
plain = fwd + bwd            # 普通训练：前向一次，反向一次
ckpt = fwd + bwd + fwd       # 激活检查点：反向时再补一次前向
print(round(ckpt / plain - 1, 2))
# 输出: 0.33

这像搬家时不留纸箱。用到时再折一个，费点工夫，但屋里宽敞。

前缀共享是推理端前缀缓存在训练端的对应物（讲义第 14 页）22:2123:01。一个 batch 里很多数据点有重复的前缀，只想算一次。难点在于还要管反向和激活内存 23:42。讲义上有两组数 24:23：

  • 长提示的 GRPO 批里，80–95% 的 token 是重复的提示 token。去重后，actor 更新最多快 6 倍。这是 Snowflake 的 ZoRRo，属于 Arctic RL 系统。
  • 多回合的 τ²-bench rollout 压成前缀树，可以压缩 9.43 倍。AReaL 的动态树注意力用深度优先遍历。沿一个分支前向，马上反向，释放这条分支的激活。然后再走下一个分支。激活内存永远不超过一条根到叶的路径。比稠密训练最多快 8.31 倍。

树形注意力掩码让分支之间互不注意。每个独立序列各有位置 ID。所有分支的梯度都累加到共享的前缀上。

并行（讲义第 15 页）24:2325:0425:4726:2927:0927:5328:41：一张卡放不下大模型，就要切到多张卡上。

方式怎么切说明
数据并行全局 batch 切成微批，每张卡一份完整模型先算出这块显存一次能处理多少 token，比如 4 万。再按这个数把序列装进微批。
流水线并行不同的层放不同的卡，如 0–8 层、9–17 层一张卡处理第 0 个微批时，前一张已经在处理第 1 个

讲师的经验法则：尽量多用数据并行，少用通信多的张量并行。这些并行在推理端同样重要。

4. 权重只传变了的那部分，MoE 的路由要照抄

两个引擎之间有两件事要做好。一是快速同步权重，二是让两边选的专家一致。

权重同步（讲义第 16 页）28:4129:21。一个 1T 参数的模型用 bf16 约 2 TB。每次更新都广播给每个推理 rank，数据量太大 30:04。RL 更新有个很好的性质，就是非常稀疏。bf16 下两次权重更新之间，大约 99% 的参数逐位不变。所以只同步差量，2 TB 变成大约二三十 GB 30:45。这样就能跨集群训练，甚至直接经对象存储上传下载。拿到参数后，仍要按推理引擎的并行布局重新切分。

w, update = 1.0, 1e-4        # 一次 RL 更新很小（示意）

# 更新不到半个格子，存成 bf16 后这个参数一位都没变。差量同步就省在这里

Rollout 路由重放（R3）（讲义第 17 页）32:2133:02。训练 MoE 时，每次前向都要选路由到哪些专家。实现上的细微差异，甚至平局，都可能让两边选了不同的专家 33:47。于是又"离策略"了。办法很直接。rollout 时记下每次推理的路由决定，随轨迹一起交给训练引擎。训练器前向时丢掉自己的决定，重放这些 34:31。这对 MoE 训练的稳定性帮助很大。讲师建议，训练 MoE 时如果损失或奖励不涨，先检查有没有开 R3。

5. 前缀一字不改只往后拼，整条轨迹才算一个数据点

序列延伸是说：每次的提示都在上一次后面接着写。上一次的提示和输出原样保留，后面加上新观察。这样整个回合能拼成一条训练序列，共享前缀只算一次。

两个外壳，哪个训练效率更高（讲义第 19 页）37:37？外壳 A 每一步都完整保留历史，往后追加新动作。外壳 B 每隔两步做一次压缩。之前的动作和观察被总结成一段摘要，再继续 38:17。课上大约六七个人选 A，十五人左右选 B 38:58。答案是 A。B 恰恰是很多生产系统的做法。Codex、Claude Code、OpenHands 都会做上下文压缩。有时序列实在太长，也不得不训练 B，但能避免就避免 39:38。

原因在讲义第 20 页 39:3840:23。A 的前缀从不中断，整条轨迹可以当 batch 里的一个数据点。把观察 token 在损失里遮掉，让优势只作用于动作 token 就行。轨迹优势 Â 会广播给每个动作 token。B 压缩之后，变成两段不连续的序列，只能拆成两个数据点 41:04。任务提示要 prefill 两遍。重复的 token 没有直接损失，却仍然要算上下文。可以用前面的动态树注意力之类的技巧，复用这部分计算。这类技巧对降低计算时间非常重要。规则是：尽可能长时间地保持完全相同的前缀，往后拼接。

6. 轨迹要存 token，不要存字符串再重新分词

rollout 里要直接存 token id 和 logprob。训练端原样使用，不经过字符串。

轨迹从推理引擎传到训练引擎，用什么格式（讲义第 23–24 页）43:1143:57？和推理引擎打交道时，很自然地用字符串。chat completions 的消息内容、提示工程、输出解析都是字符串 44:39。所以很多框架起初就传字符串，让训练端重新分词。很快大家都发现这是错的 45:21。应该存 token，直接把 token 交给训练引擎 46:0146:43。原因有两个：

  • 字符串空间里很小的变换，会导致很大的分词差异。比如训练端的模板在某处多插了一个空白。重新分词后，就和推理端采到的 token 不一样了。你就在训练和推理不同的 token，也就是离策略了。
  • 分词是一对一的，反分词是多对一的。一段文字分词，得到规范的 token，比如整词 Hello。但模型不一定产生规范的那组 token，可能产生 H + ello。传字符串再重新分词，训练端拿到的是 Hello。推理端采的却是 H、ello。
vocab = {1: "H", 5: "ello", 2: "He", 6: "llo", 4: "Hello"}   # 讲义的玩具词表
sampled = [1, 5]                                      # 模型采出来的是 H + ello
text = "".join(vocab[i] for i in sampled)
retok = [i for i, s in vocab.items() if s == text]   # 重新分词，拿到规范的整词
print(text, sampled, retok)
# 输出: Hello [1, 5] [4]
# 踩坑：采样时记的两个 logprob 对不上训练端的一个 token，掩码、重要性比率全错位。He + llo 也一样
# 作业 3 考点：智能体在 token 空间里拼上下文，采样时的 logprob 直接存进 TokenSequence
# 作业 3 考点：同步训练时比率应该非常接近 1。不接近，多半是 logprob 挂错了 token

这像把照片打印出来再扫描回去。看着一样，像素早就不是原来那些了。早期很多框架因此出现奇怪的损失尖峰和训练不稳定。现在几乎所有 RL 框架都记录确切的 token，传给训练引擎。

7. 异步要让推理和训练分开跑，推理还得能半路换权重

8. 把每块做成服务，换外壳不用改代码

好框架把推理、训练、外壳都做成服务，彼此只说标准协议。

外壳无关（讲义第 29 页）53:11。流行的外壳很多，Codex、Claude Code、OpenHands、Pi、Hermes、Prime Agent，每天都有新的。每加一个外壳就要改框架代码，甚至 fork 仓库，很糟糕 53:52。很多框架改用"中间人"模式。在推理引擎和外壳之间放一个代理服务。它模仿外壳本来就会说的推理 API，比如 chat completions、responses。它把请求转给推理引擎，把回答转回外壳。顺手把训练需要的数据存进 rollout 存储，比如 logprob、R3 的路由记录 54:35。这个代理只写一次，作为框架的一部分。换外壳不用改一行代码。甚至可以直接给外壳一个 chat completions 的地址。

store = []
def proxy(request):  # 中间人：外壳以为自己在调普通的推理 API（示意）
    store.append({"request": request, "logprobs": [-0.1]})   # 顺手记下训练要的数据
    return "ls"                                              # 推理引擎的回答原样转回外壳
print(proxy("list files"), store)
# 输出: ls [{'request': 'list files', 'logprobs': [-0.1]}]

这像连锁店的中央厨房。各店只按统一的单子下单。厨房里换了人，店里照样营业。

单程序多数据（SPMD）（讲义第 30 页）54:3555:18。这是写过分布式代码的人熟悉的模式。每个 GPU rank 跑同一份 Python 程序，按 rank 条件执行不同的部分 55:58。比如 rank 0–3 组成训练组，做 FSDP 的集合通信和优化器更新。rank 4–7 组成推理组，做张量 / 上下文并行解码和权重刷新。好处是一个程序就是全部。全局一目了然，想改就改，直接控制一切。缺点是很不灵活 56:40。AReaL 在 1.0 之前就是这种模式，后来转向了下面这种。

一切皆服务 + 单一控制器（讲义第 31–33 页）56:4057:22。一个中央编排器负责协调各个服务。有训练服务、推理服务和权重同步服务。还有智能体外壳，以及环境 / 奖励服务 58:04。它们之间说标准协议。外壳和环境工具之间用 MCP，推理用 chat completions / responses，训练用 Tinker 训练 API 58:45。讲义上的服务边界和 API 是示意。

  • 关注点分离：推理服务、训练服务各自都非常复杂、专门。只要协议一致，就能各自独立开发和维护。可以直接用别人做得极好的服务，自己专注其他部分。编排器只是一个跑在 CPU 上的轻量训练循环。它不要 GPU，也没有复杂依赖。研究者很容易试不同的算法。
  • 模块化：问"该用哪个 RL 框架"？只要说同一套 API，就能互换。Tinker API 最早是 Thinking Machines 为它的托管训练服务提出的。现在 Miles、SkyRL 等开源框架也实现了它。外壳和推理引擎（vLLM、SGLang）也都能换。
  • 弹性扩容和异构算力（讲义第 34–36 页）59:271:00:08：控制器后面能挂任意多的推理服务。训练中途随时可以加。而且不必一样，NVIDIA 的卡和 AMD 的卡可以各跑一个。

讲义第 37 页的例子是 AstraFlow，CMU 一位博士后在做 1:00:08。它是 rollout 即服务，可以用各种 GPU，随时加入。训练服务通过权重服务，把权重推给所有推理服务器。地图上的数据和权重在各大洲之间流动 1:00:49。服务化还让这些事变得容易：

  • 多策略训练（讲义第 38 页）1:00:491:01:32：现在的多智能体训练，多半共用一个模型。服务化之后，各个智能体可以用不同的权重，甚至不同的结构。各配各的训练器和推理引擎。
  • 在线 RL（讲义第 39 页）1:01:321:02:13：把已部署的外壳也当成一个服务。它偶尔给训练服务送数据，模型部署后还能持续更新。外壳可以是 Hermes、OpenHands，或者 IDE 里的 Cursor。讲师说 Cursor 的 Tab 模型和 Composer 模型都有这样的流程。它们一直从用户那里收集数据，更新后上线新版本 1:02:55。按它的博客，用 Composer 的自动模式时，新检查点换得很勤。大约每 5 小时就可能换一个。
  • 多租户、多 LoRA 训练（讲义第 40–41 页）1:02:551:03:35：托管训练服务有很多用户。每人都想训自己的模型。给每个用户的运行一份 LoRA 权重。再用专门的 kernel（Grouped-GEMM / SGMV）让多份 LoRA 的前向和反向并发执行 1:04:17。讲义的对比用 8 个 GSM8K 任务，模型是 Qwen3-4B。8 个并发运行都在约 90 分钟内完成。串行时 Job 2、3、8 要到 230–250 分钟。单个并发运行比单个串行运行慢，但总吞吐高得多 1:04:58。开源实现来自 SkyRL 等，Tinker 是最早这样做的服务之一。

Tinker 的 API 很简洁 1:05:38。每个训练运行配一个训练客户端。每个 LoRA 检查点配一个采样客户端。操作只有四个：

  • forward_backward：前向和反向，累积梯度
  • optim_step：按累积的梯度更新
  • sample：为交互、评测或 RL 生成 token
  • save_state：保存进度，以便恢复

本讲开头那组操作的拆分，就来自这里。好处是不用操心切分和算力，按服务付费。而且代码对着 Tinker API 写，之后也能换到 SkyRL 或 Miles 的开源实现上。那样就用自己的 GPU 跑同样的训练循环。

weights = {"v0": "base"}                       # 采样端能用的权重版本（示意）
def save_weights_for_sampler(name, w): weights[name] = w
def create_sampling_client(name): return lambda prompt: weights[name] + " says: " + prompt
save_weights_for_sampler("v1", "lora-step1")   # 训练完一步，把新权重存给采样端
print(create_sampling_client("v1")("fix the bug"))
# 输出: lora-step1 says: fix the bug
