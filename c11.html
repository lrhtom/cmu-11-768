重排序与评判模型（11 月 12 日）

重排序就是同一个问题多采几个候选。再让一个打分器，挑出最好的。打分器有三种。能执行的验证器，学出来的评判模型，按 rubric 打分的 LLM 评审。候选越多，"至少有一个对"的机会越大。可最后挑得准不准，全看打分器。结果奖励只看最后对不对，过程奖励给每一步打分。评判模型说到底就是价值函数。它预测从这里往后还能拿多少奖励。可以每走一步挑一次，也可以整条做完再挑。打分器会冤枉好解，也会放过坏解。候选采得越多，越容易碰上一个专门骗过它的错解。

1. 重排序就是多采几个候选，让打分器挑最好的那个

重排序（reranking）就是同一个问题采好几个答案，打完分再挑。生成的模型一点不改，只多花推理的算力：

cands = ["x > 0", "x >= 0", "bool(x)", "x < 0"]  # 同一个空采 4 个候选：def is_positive(x): return ___（示意）
tests = [(1, True), (0, False), (-2, False)]
score = {c: sum(eval("lambda x: " + c)(x) == y for x, y in tests) for c in cands}  # 打分器：数过了几个测试
print(max(score, key=score.get), score)
# 输出: x > 0 {'x > 0': 3, 'x >= 0': 2, 'bool(x)': 2, 'x < 0': 1}
# 只采 1 个、碰巧采到 x >= 0，就错了。采 4 个再挑，就稳了

这像招聘。先多收几份简历，再按同一套标准打分，挑最高的。简历收得多是一回事，打分标准准不准是另一回事。

2. 打分器有三种：跑测试的验证器、学出来的评判模型、LLM 评审

能跑测试就跑测试。跑不了测试，就训一个模型来预测对不对。连训练数据都没有，就请大模型按 rubric 判。三种写成函数是这样：

def test_verifier(out): return float(out == "0")  # 能执行：跑测试，非 1 即 0
def critic(out): return {"0": 0.8, "3": 0.3}.get(out, 0.5)  # 学出来的：给一个 0 到 1 之间的分，示意
def llm_judge(out, rubric): return sum(w for check, w in rubric if check(out)) / sum(w for _, w in rubric)  # 按 rubric 加权，示意
print(test_verifier("3"), critic("3"), round(llm_judge("3", [(str.isdigit, 2), (lambda o: o == "0", 1)]), 2))
# 输出: 0.0 0.3 0.67
# 踩坑：三个分的含义不一样，不能直接拿来比大小，也不能随手相加

这像判卷。选择题对答案，一秒判完。作文给老教师看，老教师是练出来的。实在找不到老教师，就发一张评分细则，请别人按条打分。

打分器怎么打分好处毛病
能执行的验证器跑测试、查最终状态。比如第 11 讲讲义第 3 页的四个用例。还有第 7 讲讲义第 27 页的程序化检查精确、便宜、能复现只查写到的东西。会冤枉好解，也会放过坏解
学出来的评判模型训练一个模型，预测成功的概率或每一步对不对（第 6 讲讲义第 50 页，第 11 讲讲义第 13、17 页）没有测试也能打分，还能给做到一半的状态打分要标注数据，也会被钻空子
LLM 评审把任务、证据、rubric 交给大模型，让它判（第 7 讲讲义第 29 页，第 17 讲讲义第 38–39 页）开放任务也能判，扩展快有偏差，有随机性，要拿人工标签校准

rubric 评审的打分公式，第 10 讲讲义第 87 页写得最清楚。每条标准 ck 有个权重 wk，评审逐条判，再加权平均：

ri = Σk wk · Judge(ck, yi)Σk wk

深度研究那一讲用它给长报告打分。还拿它当强化学习的奖励。见第 4 章的深度研究一讲。第 17 讲讲义第 39 页的 rubric 分四类。正确性、完整性、任务要求、技术质量。

3. 候选越多，"至少一个对"越容易，可挑不挑得中全看打分器

采 N 个候选，至少有一个对的概率是 1 − (1 − p)N。这是神谕重排序的上限。打分器有噪声时，真挑中的会差一大截：

p, N, noise = 0.3, 8, 1.0  # 单个候选做对的概率、候选数、打分器的噪声（示意）
runs = [[random.random() < p for _ in range(N)] for _ in range(20000)]  # 每次采 N 个，记下各自对不对
picked = [max(r, key=lambda c: c + random.gauss(0, noise)) for r in runs]  # 打分 = 对不对 + 噪声，挑分最高的
print(round(1 - (1 - p) ** N, 3), round(sum(picked) / len(picked), 3))  # 神谕上限 vs 实际挑中
# 输出: 0.942 0.613
# 踩坑：多采候选只抬高了上限。打分器不准，大部分好处到不了手

这像在一堆钥匙里找能开门的那把。钥匙越多，里面有对的那把越有把握。可要是你只能凭手感挑一把去试，钥匙再多也白搭。

4. 结果奖励只看最后对不对，过程奖励给每一步打分

结果奖励模型（ORM）只看终点，给整条一个分。过程奖励模型（PRM）一步一步判，能指出错在哪一步：

steps = ["x/(3*x-7) == 2/5", "5*x == 2*(3*x-7)", "5*x == 6*x - 14", "x == 7"]  # 第 11 讲讲义第 17 页的解题步骤（节选，写成 Python）
orm = eval(steps[-1], {"x": 14})  # 结果奖励：只看最后的答案
prm = [eval(s, {"x": 14}) for s in steps]  # 过程奖励：每一步都判（这里拿真答案 14 代进去，示意）
print(orm, prm)
# 输出: False [True, True, True, False]
# 踩坑：结果奖励只说"错了"。过程奖励指出前三步都对，错在最后一步

这像改数学卷子。只看答案的老师打个叉就完了。看过程的老师会在错的那一行画圈，前面写对的还给分。

  • 第 11 讲讲义第 17 页的例子。分母比分子的 3 倍少 7，分数等于 2/5，问分子是多少。答案是 14。前五步都对。由 5x = 6x − 14 得出"x = 7"，标注员把这一步标成错。
  • 讲义给 PRM 的定位是价值的替身。它从人工标注里学每一步对不对。用它代替"从这一步往后还能拿多少奖励"。
  • 为什么需要逐步的分（第 11 讲讲义第 9 页）。成功的轨迹里也可能有一步走错。失败的轨迹里也可能有一步走对。只给整条一个分，这些都分不出来。
  • 只看结果会漏掉违规（第 7 讲讲义第 39 页）。任务是把 20 美元以下的蓝色杯子加进购物车，别下单。最终状态检查通过，过程检查却发现它下了单，判失败。
  • 部分分是折中（第 11 讲讲义第 45 页）：按通过的检查项给分，组里的分数就拉开了。代价是可能被钻空子，第 7 节再说。

逐步打分的代价是要标注每一步，比只标结果贵得多。第 11 讲的价值函数、优势，见第 6 章第 1 讲第 3、4 节。

5. 评判模型就是价值函数：预测从这一步往后还能拿多少奖励

评判模型（critic）学的是一个平均数。从当前历史出发，按现在的策略接着跑，平均能拿多少奖励。最好的预测就是那些结果的平均：

outcomes = [0, 1, 0, 0, 1, 0, 0, 0, 1, 0]  # 第 11 讲讲义第 12 页：从同一个历史接着跑 10 次的结果
V = sum(outcomes) / len(outcomes)  # 价值的估计：平均能拿多少奖励
mse = lambda v: sum((v - r) ** 2 for r in outcomes) / len(outcomes)  # 第 11 讲讲义第 13 页：用平方误差训练
print(V, round(mse(0.6), 2), round(mse(V), 2))
# 输出: 0.3 0.3 0.21
# 踩坑：价值是"按现在这个策略接着跑"的平均。策略一变，同一个历史的价值也跟着变

这像天气预报说"降水概率 30%"。它不是说一定下或一定不下。而是同样的天气形势里，十次有三次下了雨。

  • 定义（第 11 讲讲义第 12 页）：Vμ(h) = 𝔼μ[R | h]。意思是从历史 h 往后，按策略 μ 接着跑能拿的奖励的期望。10 次采样只是对它的估计。
  • 训练（第 11 讲讲义第 13 页）：评论家 Vφ 用平方误差去拟合真实的后续奖励。预测 0.6 时误差 0.30，预测平均值 0.3 时误差最小，是 0.21。
  • 长在哪（第 11 讲讲义第 14 页）。可以是单独一个价值网络。也可以在策略模型身上接一个线性的价值头。后者要挡住梯度，别让价值损失改动策略的主体。
  • 拿来做逐步的评判（第 11 讲讲义第 15 页）。比较一个动作前后的价值，就知道这一步是帮忙还是添乱。下面演示的后半段就是这一页的数。

训练时的评论家，推理时的评判模型，其实是一个东西：

用在哪拿价值做什么本课的例子
训练（RL）算优势，告诉策略这一步比预期好多少PPO 和 GAE，见第 6 章第 1 讲第 4 节

6. 可以每走一步挑一次，也可以整条做完再挑，前者要能给半路打分

整条做完再挑，只需要会判终点。每一步都挑，要能给做到一半的状态打分。可一旦能做到，效果差很多：

p, T, k = 0.5, 5, 4  # 每一步做对的概率、步数、每次采几个（示意）
per_step = (1 - (1 - p) ** k) ** T  # 每一步采 k 个，挑对的那个（要有能判每一步的打分器）
whole = 1 - (1 - p ** T) ** k  # 整条跑 k 次，最后挑一条（神谕重排序）
print(round(per_step, 3), round(whole, 3))
# 输出: 0.724 0.119
# 踩坑：打分器在半路不准，每一步的误判也会一路累积

这像走迷宫。整条走完再挑，像派四个人各走一遍，看谁出来了。每步都挑，像每到一个岔口先探头看一眼再走。

  • 五步任务，每步做对的概率 0.5，整条做对只有 0.55 ≈ 0.03。整条跑 4 次再挑，也只有 0.119。长任务里准确率连乘，见第 3 章第 9 节。
  • 第 5 讲讲义第 24 页比了三种花 token 的方式。思维链写长一点，每步采多个再挑，和环境多交互。同样多的 token，和环境多交互大多最划算。
  • 树搜索在两者之间。它每步在真实环境里展开几个候选，用价值函数打分。走不通还能回溯。树搜索论文里，它比整条轨迹重排序好得多，见第 21 讲第 7 节。
  • 整条轨迹重排序还有个实际问题。轨迹要走完才能评。中途做了下单这类撤不回的动作，挑的时候已经晚了。

7. 打分器会冤枉好解，也会放过坏解，候选越多越容易碰上骗过它的错解

验证器有两种错。假阴性是把好解判错，假阳性是把坏解判对。第 11 讲讲义第 41 页的假阳性，几行代码就能复现：

cands = {"fix": lambda c: 3 if c.get("retries") is None else c["retries"], "hack": lambda c: 0}  # 第 11 讲讲义第 41 页
weak = lambda f: f({"retries": 0}) == 0  # 训练用的验证器只测了 retries=0
full = lambda f: all(f(c) == y for c, y in [({}, 3), ({"retries": None}, 3), ({"retries": 0}, 0), ({"retries": 2}, 2)])
print({k: (weak(f), full(f)) for k, f in cands.items()})
# 输出: {'fix': (True, True), 'hack': (True, False)}
# 踩坑："永远返回 0"也拿满分。拿它挑候选或当奖励，就是在奖励作弊

这像只查"有没有交作业"的老师。交一张白纸也算交了。查得越松，白纸越多。

  • 假阴性（第 11 讲讲义第 39 页）：规则要求代码里出现 value is None 这几个字。一个四个用例全对、写法不同的解被拒了。要查行为，别查措辞。
  • 假阴性多了，分数会卡在 100% 以下（第 11 讲讲义第 40 页）。SWE-bench Verified 卡在约 81%，剩下的失败很多是测试有问题。
  • 假阳性（第 11 讲讲义第 41–42 页）：训练只测一个输入，"永远返回 0"就过了。环境里的现成捷径也不少。能上网，能看 Git 历史，有别的模型的 API 密钥，能碰测试。
  • 辅助奖励也会被钻（第 11 讲讲义第 46 页）。给"用了网页工具"加分有 bug，模型就把浏览器当计算器用。某种人设下"小妖精"之类的比喻得分高，这类比喻就越用越多。
  • 要有独立的检查（第 11 讲讲义第 43 页）。训练奖励涨了，独立的检查却没涨，就去翻轨迹找捷径。

挑选会放大假阳性，这是笔记的推论。假设每个候选有 5% 的概率是"骗过打分器的错解"。只采 1 个，碰上的概率是 5%。采 4 个，变成 18.5%。采 16 个，变成 56.0%，本机算的。打分器又偏偏会给它高分，挑中它的机会就大了。

打分器不完美也不是没用。第 4 讲讲义第 40 页做过一个实验。把评审换成模拟的，真标签按固定概率翻转。效果确实随评审准确率变化。可在很宽的准确率范围里，都还有提升。

8. LLM 评审能扩展但有偏差：判多次取平均，换家族交叉判，再拿人工标签校准

LLM 评审每次判的分会晃，还会偏向自家模型的输出。多判几次取平均，能压住晃动，可压不住偏向：

true_q = 0.6  # 一份答卷真实的得分率（示意）
judge = lambda bias=0.0: min(1.0, max(0.0, true_q + bias + random.gauss(0, 0.2)))  # 单次评审：有随机性，可能偏向自家
print([round(judge(), 2) for _ in range(3)], round(sum(judge() for _ in range(20)) / 20, 2))  # 判 3 次差很多，20 次取平均就稳了
print(round(sum(judge(0.15) for _ in range(20)) / 20, 2))  # 自家模型当评审：取了平均照样偏高
# 输出: [0.79, 0.32, 0.46] 0.59
# 输出: 0.72

这像体育比赛的打分。去掉最高分和最低分，能压住个别裁判手抖。可要是裁判和选手是同乡，平均多少次也去不掉偏心。得换人来判。

  • 偏差（第 17 讲讲义第 42 页）：LLM 评审能扩展，但更容易高估自家的回答。它的输出有随机性，看图的判断也差。
  • rubric 写不完美（第 17 讲讲义第 43 页）：好的 rubric 因模型、因用户而异。
  • 要人工校准（第 7 讲讲义第 29 页）：灵活的证据评判，必须拿人工标签校准。第 7 讲讲义第 30、32 页里有两个网页评测。它们的评审和人的一致率分别是 85.3% 和 85.7%。评审质量本身成了分数的一部分。
  • 人来裁定（第 7 讲讲义第 33 页）：两个评审一个判通过、一个判失败时，拿证据来裁。人工复核既能直接打分，也能审计自动评审。
  • 评审要有人告诉它查什么（第 15 讲讲义第 33 页）。评审看智能体翻 Git 历史，起初只给 2/10 的可疑度。给了漏洞的链接，才改成 7/10。

做法压住什么在哪见过
同一个评审判多次取平均随机性树搜索的裁判判 20 次。只判 1 次 28.5%，平均 20 次 37.0%（第 21 讲第 3 节）

下一讲的树搜索，就是把这一讲的评判模型放进一棵搜索树。树在真实环境里展开。打分器越准，搜索越值钱。

树搜索：让网页智能体在真实环境里展开、打分、回退

树搜索就是每走一步之前，先在真实网站里试几条路。然后挑分最高的那条走。普通的网页智能体走一步算一步，只看当前页面就决定动作。一步走错，后面越错越远，也没法回头。论文在每一步执行之前，先做一次最佳优先树搜索。智能体提出几个候选动作，真的去执行。一个多模态大模型当"裁判"，给到达的页面打 0 到 1 的分。分高的先探索。回溯靠"重置到起点，再重放动作序列"。搜到够好的页面或者预算用完，就走到最好的那个状态。模型还是同一个，也不重新训练。VisualWebArena 上，GPT-4o 智能体的成功率从 18.9% 提到 26.4%。而且搜索预算越大越好。

这一节的依据：第 21 讲（11 月 17 日，JY Koh）还没上。下面的内容来自讲者本人的论文。作者是 Koh、McAleer、Fried、Salakhutdinov，Tree Search for Language Model Agents，TMLR 2025（arXiv 2407.01476v3）。PDF 26 页全文已读。元数据经 arXiv、OpenAlex、DataCite 三处核对，证据在 evidence/。"这一讲会讲这篇论文"，是我们根据讲者和作者身份做的推断。课上完要核对。

1. 一步一步走不能回头，错误会连乘，所以要在推理时搜索

走一步算一步的智能体，错一步就只能带着错往下走。步数一多，成功率按乘法往下掉：

p = 0.9  # 示意：每一步做对的概率
for n in [1, 5, 10]:
    print(n, round(p ** n, 2))  # n 步全做对的概率
# 输出: 10 0.35
# 第 3 章讲过：长任务里准确率是连乘的。能回头，才能把错的那一步换掉

这像走迷宫只许往前，不许退回岔路口。论文开头给了一个对比。WebArena 和 VisualWebArena 是两个很真实的网页测试集。人在上面能完成 78% 和 89% 的任务。最好的智能体通常不到 20%。作者认为一个重要瓶颈在于，智能体不会用测试时的算力。它不会探索和多步规划。

  • 大多数做法把任务当成部分可观测的决策过程。它们只拿当前观察决定下一步。错误逐步累积。一旦走到坏状态，就很难改回来。
  • 网页上能做的动作，比大多数游戏或文字模拟器多得多。常常有好几个看起来都合理的动作，要排成序列。
  • 下棋、围棋、扑克里，"搜索"一再被证明有效。搜索就是不断构建、探索、剪枝一张由中间状态组成的图。
  • 但网页任务不像游戏有明确的输赢信号。做到一半时，不知道离成功还有多近。

所以要两样东西。一个是能给"做到一半"打分的价值函数。另一个是在真实环境里搜索、能利用环境反馈的算法。论文强调，搜的不只是模型的文字输出。它搜的是真实网站的状态。

2. 底座智能体不用重新训练，搜索直接套在外面

候选动作是从同一个模型里多采几次、数票数得来的。每一步让模型用思维链生成 20 次输出。数一数每个动作出现几次，取最多的前 b 个当分支：

samples = ["click [罐头]"] * 9 + ["type [搜索框] [Del Monte]"] * 7 + ["scroll [down]"] * 4  # 20 次采样，票数是示意
b = 2  # 分支数
print(collections.Counter(samples).most_common(b))
# 输出: [('click [罐头]', 9), ('type [搜索框] [Del Monte]', 7)]
# 踩坑：采样要有随机性（论文用温度 1.0、top-p 0.95），不然 20 次全一样，分不出叉

这像让同一个人写 20 张便利贴。再挑出现最多的两个主意。采样用的是 nucleus 采样，温度 1.0，top-p 0.95。

实验用 (Visual)WebArena。环境由状态、动作和确定性的转移函数组成。每个任务有一条自然语言指令。比如"帮我找 2000 美元以下最便宜的红色丰田车"。还有一个判 0 或 1 的奖励函数。动作有 12 种（论文表 1）：

  • 点击、悬停、输入、按键。
  • 新开、切换、关闭标签页。
  • 打开网址、后退、前进、上下滚动。
  • 结束并给出答案。

底座是现成的、靠提示词驱动的智能体。搜索套在外面，不需要重新训练：

底座看到什么
多模态 SoM（GPT-4o）网页截图，每个可交互元素都画了框、编了号。外加元素列表的文字。
加图片说明（Llama-3-70B-Instruct，不能看图）网页的无障碍树。图片用现成的说明模型（BLIP-2）转成文字。
纯文字（WebArena 上的 GPT-4o 和 Llama-3-70B）无障碍树

3. 价值函数就是让大模型当裁判，判 20 次取平均

价值函数估计当前状态的期望奖励。真正的目标状态得满分 1。模拟器的真实状态（比如网站数据库）智能体看不到。所以它只能根据任务指令和看过的观察来算（论文第 3.2 节）：

vt = fv( I, {o1, …, ot} ) ∈ [0, 1]

裁判每次只给三档。成功记 1，失败记 0，"失败但在正轨上"记 0.5。判 20 次再平均，分数就细了：

votes = [1] * 6 + [0.5] * 10 + [0] * 4  # 同一状态判 20 次，票数是示意
print(sum(votes) / len(votes))
print(sorted(set(votes)))  # 只判 1 次，分数只能落在这三档上
# 输出: 0.55
# 输出: [0, 0.5, 1]
# 消融（论文第 5.1 节）：只判 1 次时子集成功率 28.5%，平均 20 次是 37.0%

这像比赛请多个评委打分再取平均。一个评委手一抖，影响就小了。具体做法：

  • 怎么实现：提示一个多模态大模型。给它任务指令、这一路的截图（最近 d 张）、做过的动作、当前网址。让它判断成功、失败，还是"失败但在正轨上"。
  • 踩坑：裁判输出的格式不合格，记 0 分。
  • 自一致：同一状态让 GPT-4o 独立判 20 次，每次先写推理。温度 1.0，top-p 1.0。取平均后，分数更细、噪声更小。
  • 代价：算一次价值比预测一次动作便宜。作者估计动作预测的 API 费用约是算价值的 2 倍。因为动作预测要放示例和整页的表示。
  • 附录说这个裁判很依赖图像。这可能是方法在多模态的 VisualWebArena 上更有效的原因之一。纯文字的 WebArena 上提升小一些。

4. 每轮取出分最高的状态去探索，孩子先带父节点的分排队

最佳优先搜索每一轮都挑清单里分最高的状态，有点像 A*。新展开的孩子不马上打分，先借用父节点的分排队：

T = {"s0": (0.3, "A B"), "A": (0.6, "A1"), "A1": (0.3, ""), "B": (0.55, "B1"), "B1": (1.0, "")}  # (裁判分, 孩子)，示意
F = [(0, "s0")]  # 待探索清单，先把起点放进去
while F:
    _, s = F.pop(max(range(len(F)), key=lambda i: F[i][0])); print(s, end=" ")  # 取出分最高的，回溯过去打分
    if T[s][0] >= 0.9: break  # 分数到阈值 θ 就停
    F += [(T[s][0], c) for c in T[s][1].split()]  # 孩子先带父节点的分入队，不立刻打分
# 输出: s0 A A1 B B1
# 踩坑：A 得了 0.6，孩子 A1 也带着 0.6 插到 B 前面。A1 其实很差，也得先试过才知道

可以想成找餐馆。先去口碑最好的那条街，街上的每家店先沾这条街的光排队。进去尝过（打分）才知道好不好，不好再退回去换街。为什么不立刻给孩子打分？因为打分要先回溯到那个状态，在网页模拟器里太贵。

超参数有四个：深度 d、分支 b、搜索预算 c，以及终止阈值 θ。前三个决定搜索树最大有多大。在执行轨迹的第 t 步，搜索从当前状态 st 开始。步骤如下（论文第 3.3 节、附录算法 1）：

  1. 建一个待探索清单 F，它是按分数排的最大优先队列。记下目前最好的状态和它的分，计数器清零。
  2. 每一轮从 F 取出分最高的状态 sp，回溯过去。用价值函数给它打分 vp，计数加 1。分数超过目前最好，就更新。
  3. 如果 vp ≥ θ，或者计数达到预算 c，就停止。前者说明大概率已经到了目标状态。
  4. 否则看到 sp 的路径到没到深度 d。没到，就让智能体提出 b 个候选动作，逐个执行。到达的新状态放进 F，先用父节点的分 vp 排队。
  5. 重复，直到停止。然后走到搜到的最好状态，把这段动作真正执行掉。t 前进相应的步数，再从新位置开始下一次搜索。

原文前后不一致（原文如此）：正文把"目前最好分"初始化为 0。更新条件写的是"严格大于"。附录算法 1 初始化为负无穷，条件写"大于等于"。算法 1 还从空的 F 里取第一个状态。实现上要先把起点放进去，上面的玩具实现就是这样做的。

5. 网页没法读档，回溯就是重置到首页再把动作重放一遍

优先队列里存的不是页面，是"从起点出发的整串动作 + 分数"。要去哪个状态，就重置环境。再从头重放它的动作序列（论文附录 A.4.1）：

F = [(("search Del Monte", "add item 1"), 0.55), (("click category",), 0.6)]  # 队列里存整串动作 + 分数，示意
def go_to(actions):
    return ["reset to home"] + list(actions)  # 先重置到起点，再从头重放
print(go_to(F[0][0]))
# 输出: ['reset to home', 'search Del Monte', 'add item 1']
# 踩坑：别用浏览器的"后退"。后退会丢掉滚动位置和输入框里已经填的文字

这像玩一个不能存档的游戏。想回到第三关，只能重开，再把前面的操作一个不差地按一遍。每执行一个新动作，就把它接到序列后面，带着分数入队。要去某个状态时，先把环境重置到起点，通常是首页。代价是很花时间。

6. 同一个模型加上搜索，成功率明显涨，弱模型涨得更多

加搜索后，四个设置的成功率都涨了。相对提升 = (加搜索 − 不搜索) ÷ 不搜索，按论文表 2 的数复算前三行：

rows = {"VWA GPT-4o": (18.9, 26.4), "VWA Llama-3": (7.6, 16.7), "WA GPT-4o": (15.0, 19.2)}  # 论文表 2
for name, (a, b) in rows.items():
    print(name, f"+{(b - a) / a:.1%}")
# 输出: VWA GPT-4o +39.7%
# 输出: VWA Llama-3 +119.7%
# 输出: WA GPT-4o +28.0%

这像给同一个学生多发几张草稿纸。底子弱的学生，草稿纸帮得更多。实验用全部 910 个 VisualWebArena 任务和 812 个 WebArena 任务。搜索参数 d = 5、b = 5、c = 20。每个任务最多真正执行 5 个动作。这是受算力和费用限制，作者预期放大会更好。最多 5 步，一部分"困难"任务就根本做不完。这类任务人要走 10 步以上（论文表 2）：

测试集智能体不搜索加搜索相对提升
VisualWebArenaGPT-4o + SoM18.9%26.4%+39.7%
VisualWebArenaLlama-3-70B + 图片说明7.6%16.7%+119.7%
WebArenaGPT-4o15.0%19.2%+28.0%
WebArenaLlama-3-70B7.6%10.1%+32.3%（正文写 32.2%，原文如此）
  • 26.4% 是当时 VisualWebArena 上最好的成绩。别人报告的 GPT-4o 不搜索、走 30 步是 19.8%。限制 5 步加搜索，反而更高。
  • WebArena 上一些别的方法分更高，表里最高 45.7%。作者说它们用了针对网站的专门技巧，或者改进的输入表示。这些和搜索不冲突，可以叠加。
  • 弱模型受益更大。加了搜索的 Llama-3-70B 在 VisualWebArena 上，接近不搜索的最强多模态模型。
  • 附录表 8：开源的 LLaVA-1.6-34B 当裁判，也有 7.6% → 13.5%（+77.6%）。整套可以完全开源复现。
  • GPT-4o-mini 自己当智能体又当裁判，9.1% → 14.4%。

7. 预算、深度、宽度和裁判，哪个都不能省

消融的结论是搜得越多越好，裁判越准越好。先看预算 c 从 0 加到 20 的相对提升：

base = 24.5  # 不搜索（c = 0），200 个 VisualWebArena 任务的子集
for c, acc in [(5, 32.0), (20, 37.0)]:
    print(c, f"+{(acc - base) / base:.1%}")
# 输出: 5 +30.6%
# 输出: 20 +51.0%

这像考试多给时间。多给一点就涨一大截，再多给还会涨。下面都在 200 个 VisualWebArena 任务的子集上，用 GPT-4o 智能体（论文第 5.1 节）：

改什么结果说明了什么
搜索预算 c0（不搜）24.5% → 5：32.0%（+30.6%）→ 20：37.0%（+51.0%）一点点搜索就有大提升，预算越大越好

改成整条轨迹重排序采 n 条完整轨迹，用同一个裁判挑最好的。约 7 条时走平在 30%。不如树搜索。c = 5 时算力和 n = 5 差不多，已有 32.0%。

为什么树搜索比"采很多条完整轨迹再挑"强？树搜索能在中途按分数回溯，剪掉坏分支。整条轨迹重排序还更不实用。轨迹要走完才能评估，很难拦住破坏性的动作。也不能中途回溯、剪掉坏分支。

按难度（全量 VisualWebArena，论文表 5）：

  • 简单：34.2% → 42.3%（+24%）。
  • 中等：12.7% → 22.2%（+75%）。
  • 困难：10.2% → 14.9%（+47%）。

作者推测，深度 5 正好覆盖了很多中等任务。困难任务需要更深的树。简单任务本来就不太需要规划。按网站（表 6、7）：所有网站都有提升。VisualWebArena 上提升最多的是分类广告（+44%）和购物（+45%）。WebArena 上是内容管理系统（+50%）。

8. 搜索救回来的，是迷路、采样运气差和裁判不完美这三种情况

论文的三个案例，分别对应搜索的三个好处。这一节是案例，没有可算的东西。可以把搜索想成带了一个能随时回到路口的向导。

  • 多步规划更稳：购物任务 #256 要把两种罐装水果加进对比清单。两种是同一品牌的。不搜索的智能体加完第一件，在第 3 步回到首页，迷路了。搜索版本探索并回溯，找到了成功路线。路线是"加第一件 → 搜索 → 加第二件"。
  • 不搜索的智能体常见两个毛病。一是撤销自己前面的动作，二是在原地打转。
  • 化解采样的不确定：分类广告任务 #48 要找含特定图片的帖子。每一步都执行第一个采到的动作，会失败。搜索在模拟器里把每个候选真的执行一遍。再用环境反馈做决定。
  • 裁判不必完美：附录里有个 WebArena 任务 #14。预算用完了，也没找到满分页面。智能体选了当时最高 0.68 的那条路，结果是对的。

9. 搜索会真的执行动作，所以下单这类撤不回的动作必须拦住

候选动作是真执行的，搜索时点了"下单"，钱就真花出去了。最简单的拦法是展开之前先过一道滤网：

DESTRUCTIVE = {"place order", "delete post"}  # 示意：手写的规则
cands = ["add to compare", "place order", "search"]
print([a for a in cands if a not in DESTRUCTIVE])  # 破坏性动作不展开
# 输出: ['add to compare', 'search']

这像试衣服可以，刷卡不行。论文列的局限：

  • 慢：c = 20 时，每轮最多要多 20 倍的模型调用。重置重放也慢。实际部署要在 b、d、c 之间权衡。
  • 破坏性动作：下单这类动作改了就撤不回。在真实网站上搜索时，必须禁止它们。作者给了几条建议：
    • 加一个分类器，预测哪些动作有破坏性，不展开它们。
    • 有领域知识时，手写规则。
    • 树搜索的好处是，约束可以直接写进价值函数。
    • 也可以训练一个"世界模型"，在模拟里搜。
    • 或者只在能撤销、能重置的场景里用搜索，比如编程、表格软件。
  • 裁判是为网页定制的：它看页面内容和浏览历史（截图）。换到软件工程智能体，可能要改成看代码执行轨迹。
  • 只试了比较简单的提示词智能体，没有结合更强的专门方法。
  • 没有专门微调裁判模型。作者认为这是有前途的方向。

10. 树搜索把前面几章的规划、评审、价值函数和权限串到了一起

这一节是对照，没有新机制。把它当成一张地图就行。它标出这篇论文用到了前面哪几块积木：

  • 第 3 章：规划、长任务里准确率连乘、"每一步挑最好的"。树搜索把"挑"变成了可以回头的探索。
  • 第 4 章：电脑操作智能体、VisualWebArena 和 WebArena 的评测方式（终态检查、LLM 评审）。这里的裁判和那一讲的 LLM 评审是同一类东西。只是这里拿来引导搜索。
  • 第 6 章：价值函数和评论家。那里在训练时用它分配功劳。这里在推理时用它决定先探索哪里。论文附录的裁判提示，就是一个零样本的价值函数。
  • 第 7 章：破坏性动作和权限。搜索时同样要限制不可撤销的操作。
