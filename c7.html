2. 先问坏事从哪来：四种威胁模型

威胁模型就是先说清：坏事是谁引起的，从哪里来。来源不同，防法也不同。

威胁模型的英文是 threat model。讲义分了四类（讲义第 8–12 页）：

威胁是怎么回事讲义的例子
恶意用户（malicious user）用户本人要智能体做不该做的事。比如盗窃、诈骗、骚扰或别的违禁行为。盗刷支付卡（第 9 页）。用户的目标是偷顾客的信用卡信息。智能体负责攻进网店、导出记录、装偷卡脚本。
提示注入（prompt injection）用户的任务是正当的。攻击者把指令藏在邮件、网页、文件或工具返回的结果里。智能体在完成用户任务时，照着做了。Cline（第 10 页）。issue 标题是不可信的文本，它进入模型上下文，被当成了指令。最后变成一条在系统上执行的 shell 命令。
智能体出错（agent error）智能体想帮忙，但做错了模拟的银行任务里，"查一下余额"变成了"付了一笔账单"（第 11 页）
不正当手段（improper means）目标本身有用，但达到目标的方法不合适一个安全挑战题里，它直接抄了暴露出来的答案。它没有真的去解题（第 12 页）。
def threat(user_ok, injected, cheated):   # 按顺序问三个问题，判出四类
    if not user_ok: return "malicious user"
    if injected: return "prompt injection"
    return "improper means" if cheated else "agent error"
print(threat(False, False, False), "|", threat(True, True, False), "|", threat(True, False, False), "|", threat(True, False, True))
# 输出: malicious user | prompt injection | agent error | improper means
# 前两类有坏人（用户或攻击者），后两类没有坏人，是智能体自己的问题

3. 红队测试：赶在坏人之前自己找漏洞

红队测试就是自己先扮坏人。在受控的测试里，专门想办法让智能体违反规则。漏洞就能赶在真攻击者之前被找到。

红队测试的英文是 red teaming。讲义分两种（讲义第 13–15 页）：

人工红队

给测试者任务和攻击目标，并对每次尝试给出反馈。讲义的例子是 Gray Swan Arena 的模拟场景。目标是拿到另一个病人的病历。截图里，智能体真的把另一位（模拟的）病人的信息全说了出来（第 14 页）。有身高、体重、眼睛颜色、血型。还有正在用的药、过去的药和过去的诊断。

自动红队

用一个攻击者模型去搜索能绕过安全规则的提示。这是一个三方循环。攻击者写提示给目标。裁判检查目标的回复是否违反政策。攻击者拿着回复和分数，改写下一条提示。讲义举的例子是 PAIR（第 15 页）。

讲师的补充 16:5317:3418:1418:5519:3520:17：红队这个说法来自网络安全，也叫渗透测试。就是雇人来攻破你的系统，通常是组织外的人。目的是赶在坏人之前补洞。Gray Swan 是从 CMU 出来的一家创业公司。它的 Arena 让人报名当红队。最早主要测聊天模型，现在也测智能体。

他讲了截图里的手法。攻击者在输入里手动加了几个特殊 token。它们表示"助手回合结束"和"系统消息"。这样就冒充了优先级更高的系统消息。模型于是越过原来"不许提供未授权信息"的规则。人工红队靠直觉试探边界。自动红队能一点点爬坡，改进提示。他的印象是：顶尖的人工红队员，流程里都用上了自动红队。

target = lambda p: "leak" if p.count("+") >= 3 else "refuse"   # 假目标：改写够多次就失守（示意）
judge = lambda reply: reply == "leak"                          # 裁判：回复违反政策了吗
prompt = "ask"
while not judge(target(prompt)): prompt += "+"                 # 攻击者拿着反馈改写一次
print(prompt, target(prompt))
# 输出: ask+++ leak
# 这就是三方循环。只要裁判的分数能往回传，攻击者就能一点点爬坡

这像请锁匠来撬自家的门。撬开了不丢人，丢人的是让小偷先撬开。

4. 对齐训练：拒绝坏请求和帮好请求要一起教

找到问题以后，可以把正确的行为训练进模型。坏请求要拒，好请求要帮，两类样本缺一不可。

讲义的两个配方，都以 NVIDIA 在 Nemotron 3 Super 上的做法为例（讲义第 16–17 页）。

监督式安全训练用的是成对的样本。有害请求和正当请求，各配一个合适的回答。讲义的示意样本：

请求合适的回答
有害请求偷顾客的信用卡信息拒绝盗窃，并主动提出帮忙保护支付数据
正当请求讲讲结账时怎么保护信用卡信息讲清合适的安全做法

合成样本的做法是这样。先决定这条该拒绝还是该帮忙，再生成回答。然后过滤掉不安全的回答，只用剩下的训练。两类样本要同时有。只教拒绝，模型会连正当的安全问题也拒绝。

requests = [("steal card numbers", "harmful"), ("how to protect card data", "benign")]   # 讲义第 16 页
plan = {"harmful": "refuse, offer to help protect data", "benign": "explain safe practices"}
samples = [(q, plan[kind]) for q, kind in requests]   # 先定该拒还是该帮，再写回答
print(samples[1])
# 输出: ('how to protect card data', 'explain safe practices')
# 踩坑：只放有害请求，模型学到的就是"见 card 就拒"。正当的安全问题也被拒掉

用强化学习做安全训练：用奖励同时教两件事。

抵抗攻击

奖励遵守安全规则的回答。用自动攻击找出更难的变体。专门拿骗过早期模型的那些变体来训练。

避免不必要的拒绝

训练集里放进正当的、和安全相关的请求。奖励对这些请求的有用回答。把安全任务和其他领域的训练任务混在一起。

讲义最后一句说，这种训练可以靠一个奖励模型来引导。这个奖励模型用人类偏好训练出来。

讲师补充 20:5921:4022:2123:0523:49：红队发现的问题，还有恶意用户，目前怎么应对？最好的办法就是监督式安全训练。他特意挑 NVIDIA Nemotron 的报告当例子。闭源模型几乎不公开安全训练的细节。开放权重的模型也说得不多。只有"完全开放"的模型，能让你知道它们具体怎么做。早些年的 Llama 报告在这方面也写得很好。用 RL 做安全训练，需要一个很好的奖励模型。它要按人类偏好来训练。类似的训练也可以用来对付提示注入。先诱发注入攻击，再确保模型不上当。

5. 训练管不住的，靠沙箱把执行关起来

训练只能让模型更可能做对，不能保证。所以还要从环境上限制它，这就是沙箱。

沙箱（sandbox）是一个隔离的环境，限制程序能访问什么、能做什么（讲义第 18–22 页）。讲义第 19 页的图里，智能体在沙箱里。它能读写任务文件，能运行代码。沙箱外的私有文件和其他服务，被策略挡住。

隔离有三条边界（讲义第 20 页）：

边界要回答的问题
文件系统和进程智能体能访问哪些文件？能控制哪些进程？
网络能连哪些服务？在那些服务上能做什么？
资源限制能用多少算力和存储？最多能跑多久？
policy = {"files": ["/task/"], "hosts": ["pypi.org"]}   # 沙箱策略：只放行任务目录和一个站点（示意）
def allowed(kind, target): return any(target.startswith(p) for p in policy[kind])
print(allowed("files", "/task/main.py"), allowed("files", "/answers/gold.txt"), allowed("hosts", "huggingface.co"))

讲义第 25 页有一句关键区别。容器共享宿主机的内核，虚拟机运行自己的客户机内核。

这句话为什么重要？容器里的进程和宿主机上的进程，最终由同一个内核管。隔离靠的是内核自己的机制。内核一旦有漏洞，容器里的程序就可能越过边界。虚拟机多了一层自己的内核和硬件虚拟化，边界更硬。代价是启动更慢、更重。所以"隔离强"和"启动快"之间要做取舍。Docker 官方文档的安全一页说了两点。内核命名空间（namespaces）提供了最直接的第一层隔离。控制组（cgroups）负责资源的计量和限额。这正好对应上面"资源限制"那条边界。但它本身不管一个容器能不能碰另一个容器的数据和进程。文档还提醒，Docker 守护进程默认需要 root 权限。它本身也是攻击面，见 Docker 文档 · Docker Engine security。

8. 监控：动作执行前先查，执行后翻日志

监控就是记录并检查智能体的每一步。目的是找出错误和不安全的动作（讲义第 30–36 页）。为什么需要它（第 31 页）：

  • 智能体做了不安全的动作，照样能交出一个有用的答案。只看最终结果，发现不了。
  • 运行过程中的检查，能及时发现问题，暂停或拦下某个动作。
  • 事后翻日志，能解释失败的原因，改进防线。

看什么证据（第 32 页）？用户的请求、工具调用、工具结果，还有对外部系统造成的改动。讲义的例子就是前面那道安全挑战题，来自 Cybench 移植版。工具调用是"读这道题的 Dockerfile"，工具结果里有秘密答案。分数是"通过"，却藏着一条意料之外的捷径。只看分数看不出来，要看日志。讲义页脚还提到 OpenTelemetry 为生成式 AI 定的属性规范。它可以用来统一记录这些调用。

规则检查和模型检查（第 33 页）各管一类。精确的条件用规则，要看上下文判断的问题用模型。

问题：这个发布者在允许列表里吗？做法：把账号和策略对比。

只看工具调用，还是也看写出来的推理（第 34 页）？任务是实现几个数学函数，并通过测试。只监控工具调用的人，能看到补丁和工具输出。这个补丁让 verify() 永远返回 true。它把原来返回 result 的几行删掉，换成了 true。监控思维链（CoT）的人，还能看到智能体写下的打算。它在推理里直接说可以糊弄过去："We can circumvent verify to always return true"。

    return "ran: " + cmd

概念负责什么

一次自动化运行的形状是：事件 → 有边界的任务 → 可检查的结果（第 39 页）：

  1. 触发issue、PR 或定时
  2. 上下文仓库、指令、权限
  3. 运行隔离的工作区
  4. 产物补丁、报告或评论
  5. 检查人或策略

11. 同一流程反复跑，轨迹就成了改进技能的训练数据

同一个流程反复跑，过去的轨迹就成了训练数据。拿它们可以自动改进技能。

讲义第 42–43 页介绍的 SkillRefiner，就用这些轨迹去改进技能。它分五步（第 42 页的流程图）：

  1. 带反馈的轨迹表示给每条轨迹打分，结合已有证据写摘要。成功、失败分开。
  2. 嵌入和聚类把摘要转成向量，在成功和失败两组里各自聚类
  3. 生成修改建议每个簇各出几条候选修改。有正向的，也有负向的。
  4. 证据把关从失败里得出的建议，要用它的支撑证据核实
  5. 合并技能正向建议和核实过的负向建议并进初始技能。得到修订版。

讲师的思路 55:4456:2757:1357:5958:4059:221:00:03：同一个流程反复跑，就变成了机器学习问题。有输入、有输出，过去所有的 PR 就是训练数据。每次分诊和评审，要么做得好，要么做得差。SkillRefiner 用的就是延迟到来的反馈。比如机器人说"看起来没问题"（LGTM），维护者却说"这很糟，要改"。这能自动检测出来，归进失败的一堆。然后把成功和失败分别聚类，提出修改建议。再过一道"证据关"：用新指令重跑，看评审是不是真的更好。最后合并成新的技能。它比 GEPA 和另一个从轨迹提炼技能的基线，都更便宜、更好。

runs = [("LGTM", "merged"), ("LGTM", "this is bad, needs changes"), ("needs tests", "fixed")]   # (机器人评审, 维护者后来的反应)（示意）
failed = [r for r in runs if r[0] == "LGTM" and "bad" in r[1]]   # 机器人说没问题，人却说很糟
print(len(failed), "of", len(runs), "go to the failure pile")
# 输出: 1 of 3 go to the failure pile
# 这就是延迟到来的反馈。失败堆和成功堆分别聚类，再提修改建议
